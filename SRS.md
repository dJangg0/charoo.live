# Charoo software requirements specification

This maintained contract guides Charoo changes and reviews; it does not certify every implementation path. Read [AGENTS.md](./AGENTS.md) for agent workflow, [ARCHITECTURE.md](./ARCHITECTURE.md) for design, and [README.md](./README.md) for commands. Preserve requirement IDs across revisions.

## Status and scope

Implementation status and open findings were reviewed against the repository on **2026-11-12**. **Changed 2026-11-22:** FR-12 now uses distinct messages for the profile reveal and drops per-owner picture consent; FR-13 (credits economy, shipped disabled), BE-08 and AD-06 are new; FR-01, FR-02, FR-06 and FR-07 reference them. Verification evidence is in the [matrix](./docs/engineering/IMPLEMENTATION_MATRIX.md). **Changed 2026-11-24:** guest capabilities and the group-room identity choice (guest or profile) are recorded in FR-01, FR-04, FR-06 and FR-13; the FR-04 join identity choice passed local unit, browser and native checks on 2026-11-24 and is now [CURRENT]; the guest wording in FR-01, FR-06 and FR-13 was not re-verified by that run. FR-06 reconnect has local domain, API and two-browser UI coverage, and it passed the native runtime on 2026-11-24; deployed runtime verification remains pending. The flags distinguish code that exists today from goals and engineering rules. **CURRENT** describes code presence, not correctness, complete test coverage, or an enabled production integration. Read the open findings before preserving current behavior; buggy behavior is not an intended requirement.

| Flag                  | Meaning                                                                                                                      |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **[CURRENT]**         | Present in the current implementation; preserve the documented behavior.                                                     |
| **[CONDITIONAL]**     | Implemented integration or feature that requires configuration or an enabled flag. Do not assume it is active in production. |
| **[TARGET]**          | Requirement for new/changed work; full compliance across the existing app has not been established.                          |
| **[POLICY]**          | Engineering or agent workflow rule, rather than a shipped application feature.                                               |
| **[NOT IMPLEMENTED]** | Absent from the current app; mentioning it does not authorize or schedule its implementation.                                |
| **[KNOWN GAP]**       | An observed limitation that remains unresolved.                                                                              |

**[ISSUE]** marks a confirmed incorrect path or known defect in an implemented feature. It is separate from presence/configuration status and links to the findings below. Flagging an issue does not authorize a fix.

When changing an implementation, update its status and relevant evidence in the same change. Distinguish source review, automated tests, runtime verification, and deployment; a build or dry run alone does not establish production readiness.

Current user instructions take precedence. Investigate code/requirement discrepancies; do not redefine requirements to match bugs. Authorized changes update affected requirements, contracts, implementation and validation together.

Charoo provides temporary conversations, shared rooms and persistent contacts. Production uses Cloudflare Workers, Durable Objects, D1, R2 and Queues. Celld supports local development and separate fleet deployment. This baseline requires no PostgreSQL, Redis or application-managed S3 connection.

## Functional requirements

- **FR-01 — Identity and consent [CURRENT]:** Guests can enter through consent and nickname confirmation. Age and sex are optional in the UI; supplied profile fields follow shared validation. Guest profile visibility defaults to private. Do not represent consent or optional profile data as verified age or identity. Authenticated sessions persist through normal navigation. A verified account receives the one-time verification bonus when credits are enabled ([FR-13](#fr-13--credits-economy)). Guests can chat in quick chat and in group rooms they join, and can add a profile picture. Guests cannot send contact, private or reconnect requests; those require a verified account, and the verification prompt explains why. Verifying through Google or email lifts these limits and grants the bonus once.
- **FR-02 — Authentication continuity [CONDITIONAL]:** Email and Google sign-in preserve pending room invitations and the profile-confirmation step. Guest upgrades preserve the applicable identity; signing into an existing account preserves that account's history. Email sign-in tokens and OAuth state are one-use; successful sign-in rotates sessions. Keep browser/session binding, PKCE, nonce and mailbox verification checks. The first verification through either path grants the one-time verification bonus when credits are enabled ([FR-13](#fr-13--credits-economy)); repeated verification grants nothing more.
- **FR-03 — Room discovery and creation [CURRENT]:** Users can create shared rooms and use invitations. **[CONDITIONAL]** Available Tonight discovery and creation require verified, online users and an enabled feature. Respect configured creation limits, categories, visibility, verified-only access, slow mode and expiry settings.
- **FR-04 — Invitation lifecycle [CURRENT]:** A full valid invitation URL opens the join flow, survives authentication, and confirms the nickname before joining. Host approval remains required where configured. Joining a group room, public or by invitation, asks the member to choose their profile picture or a generated avatar for that room. The choice is saved with the join or approval request. Group rooms do not require a profile picture. A picture choice pins the member's approved picture for that room; replacing it stops its display. Members cannot change the choice in this version. Each room join, public or by invitation, also asks whether to enter with the member’s profile or as a guest. A guest entry takes an optional nickname of 2 to 24 characters; without one, the room shows a random name such as “Guest 3F2A”. Other members and the host’s join-request list see only that name, a generated avatar and no verified badge. A guest entry never shows a profile picture or the account's age, gender and region, and it cannot send or receive contact or private-chat requests in that room, because those carry the account name. Messages keep the name they were written under, so a later profile rejoin does not reveal earlier guest messages. The choice is saved with the join or approval request and is asked again on every join. Available Tonight rooms require a verified account, so unverified guests enter shared group rooms only. Staff keep access to the account for reports and moderation under the audited rules in FR-07 and FR-08. Limitation: other members still receive the account’s opaque user identifier, as they do today; the choice hides names and pictures, not identifiers. Pending users can cancel; hosts can approve or reject. Closed, expired, removed or blocked access must not bypass room rules. **[ISSUE]** [IMP-01](./docs/IMPLEMENTATION_REVIEW.md#imp-01), [IMP-03](./docs/IMPLEMENTATION_REVIEW.md#imp-03).
- **FR-05 — Conversations [CURRENT]:** Authorized members can load paginated history, send messages, reply, react and record read receipts. Writes use stable client message IDs so retries create one message. The client runs one active-room refresh at a time and queues a follow-up for newer invalidations. Read receipts advance when newly fetched incoming messages need acknowledgement. Typing is transient. Room slow mode remains configurable for supported rooms; quick chat has no per-message delay. There is no global per-user 40-messages-per-minute cap on message submissions. **[TARGET]** Changed UI flows must tie successful actions to authoritative backend results and provide understandable pending, error and retry states; complete UI coverage is not established. **[ISSUE]** [IMP-06](./docs/IMPLEMENTATION_REVIEW.md#imp-06), [IMP-07](./docs/IMPLEMENTATION_REVIEW.md#imp-07).
- **FR-06 — Matching and relationships [CURRENT]:** Quick chat supports queueing, cancellation and Next, without room slow mode. Searches end after **two minutes** if no match is made; the client stops polling and cancels the server queue, and the Matcher expires queue entries at the same deadline. A match established before that deadline takes precedence. A later search starts a fresh two-minute window. Starting a new quick-chat search requires an approved profile picture; the Matcher refuses the request with `Add a profile picture before starting a quick chat` and the client shows that message. Returning to an existing active room is not blocked. Exclude blocked users and recent pairs according to configured rules. Quick-chat matching reads the profile gender value `Male`, `Female` or `Other` (case-insensitive) only to choose pairings: male–female, male–other, female–other and other–other pairs, and pairs where either gender is unset, match immediately; male–male and female–female pairs wait until the earlier-queued participant has waited **one minute**, after which any pair may match. The Matcher returns only a room ID and does not expose gender. Private/contact requests preserve consent and deduplication. A verified user with an eligible archived quick chat can request reconnection. Guests can finish quick chats normally but cannot request reconnection; the reconnect control shows a verification prompt instead; the recipient explicitly accepts or rejects the request. Acceptance opens a private chat. Rejection removes the originating archive from the requester's past quick chats so the rejected connection cannot be requested again from that archive. Requests and archives expire, and current block checks still apply. Reconnect requests are free to send. While credits are enabled ([FR-13](#fr-13--credits-economy)), the reconnect price is charged to the requester when the recipient accepts; a requester who cannot pay is refused before sending, and an acceptance that finds insufficient credits creates no room. While credits are enabled, saved contacts are limited to the free contact slots plus purchased slots, and a contact can be saved from a quick chat only after both participants reach the profile milestone in FR-12. Contact removal and blocking stop the relevant private interaction. Quick-chat archives obey retention and reconnect eligibility. Implementation and verification limits are recorded in the [matrix](./docs/engineering/IMPLEMENTATION_MATRIX.md#fr-06--matching-and-relationships).
- **FR-07 — Moderation and privacy [CURRENT]:** Hosts can close rooms, remove members with a reason, and mute/unmute members. A mute prevents messages, reactions and attachments while retaining permitted reading. Users can block, unblock and report. Stranger ASL disclosure requires qualifying participation and still respects profile visibility. The ASL and profile-picture milestones follow FR-12 below, and a paid early peek follows FR-13; participation alone must not disclose a picture. Reports and staff evidence access must remain authorized and audited. **[ISSUE]** [IMP-01](./docs/IMPLEMENTATION_REVIEW.md#imp-01), [IMP-03](./docs/IMPLEMENTATION_REVIEW.md#imp-03).
- **FR-08 — Administration [CURRENT]:** Support, moderator and administrator capabilities are role-checked per operation. Preserve settings, report handling, bans/suspensions and audit records. Staff role grants remain an operator action, not a public self-service endpoint. Local no-auth administration must never bypass production authentication.
- **FR-09 — Optional integrations [CONDITIONAL]:** Email needs Mailpit locally or Resend in production; Google needs its complete credential group; room attachments need the authenticated scanner; profile pictures use the authenticated private upload flow in FR-12; video needs LiveKit; assistant suggestions need a compatible provider. Video and assistant features also require their admin flags. Missing configuration must return an explicit unavailable result. Assistant requests omit conversation history; video tokens require both participants' consent and are call-scoped. **[ISSUE]** [IMP-02](./docs/IMPLEMENTATION_REVIEW.md#imp-02).
- **FR-10 — Expiry and cleanup [CURRENT]:** Apply configured room, guest, request and call deadlines during authorization, before cleanup executes. Temporary conversations and archives expire; contact conversations follow their distinct lifecycle. Cleanup removes expired private content and media, retains necessary version tombstones, and anonymizes eligible retained report/audit identities. **[ISSUE]** [IMP-04](./docs/IMPLEMENTATION_REVIEW.md#imp-04).
- **FR-11 — User-centered UI quality [TARGET]:** For every new or changed user-facing flow, review the experience from the affected user's perspective and make the frontend state match what is actually happening. For each applicable stage, provide clear, accessible feedback and useful next steps for waiting/loading or measured progress, empty/unavailable states, success, failure/retry/recovery, and cancellation. Do not imply exact progress when it is not measured. Preserve narrow/mobile and desktop usability, keyboard operation, visible labels/focus, readable themes, invitations, drafts and navigation intent across relevant asynchronous updates. Treat these states as part of feature acceptance and verify them through the affected user flow. **[ISSUE]** [IMP-05](./docs/IMPLEMENTATION_REVIEW.md#imp-05), [IMP-06](./docs/IMPLEMENTATION_REVIEW.md#imp-06), [IMP-07](./docs/IMPLEMENTATION_REVIEW.md#imp-07).
- **FR-12 — Quick-chat ASL and profile-picture reveal [TARGET]:** Show two progress bars in quick chat: words toward permitted ASL, and distinct messages toward the profile reveal. Each participant must contribute **at least ten words** in the same room before ASL appears (`quickchat_asl_word_threshold`), and **at least ten distinct messages** before profile pictures appear (`quickchat_picture_message_threshold`). Until these milestones are met, the chat hides the corresponding reveal. At the ASL milestone, show only the other participant’s ASL fields allowed by their profile preferences under that stranger’s name in the room-members list in the left sidebar. At the profile milestone, each participant sees the other participant’s current approved profile picture. There is no per-owner consent prompt: the quick-chat entry screen discloses that a profile picture is shown to the partner after the milestone. A paid early peek ([FR-13](#fr-13--credits-economy)) is the only other early reveal, and it is one-sided. The authenticated private JPEG, PNG or WebP upload path accepts files up to 5 MB and applies server-side format, size and container checks. See the [implementation matrix](./docs/engineering/IMPLEMENTATION_MATRIX.md#fr-12-implementation).

The executable public shapes are in [packages/contracts/src/index.ts](./packages/contracts/src/index.ts); route behavior lives in [celld/features](./celld/features). Validate changes across both boundaries.

### Quick-chat disclosure milestones (FR-12)

**Changed 2026-11-22.** The profile reveal moved from twenty words each to ten distinct messages each, with per-owner consent removed. Thresholds are admin settings (`quickchat_asl_word_threshold` 2–20, default 10; `quickchat_picture_message_threshold` 1–50, default 10); the stored caps are 20 words and 50 messages per participant. “Show profile” means showing an existing **profile picture** to the other quick-chat participant. It does not grant access to another conversation or a public image URL. ASL means **age, sex and location**, currently `age`, `gender` and `region`; show only supplied values, subject to the owner’s existing ASL visibility preferences. These values are not verified age, identity or precise device location.

| Milestone | Required contribution in the current quick chat | Result |
| --- | --- | --- |
| ASL | Each participant has contributed at least the ASL word threshold (default 10 words) | Show each viewer only the other participant’s permitted ASL under their name in the left room sidebar. |
| Profile reveal | Each participant has sent at least the message threshold (default 10 distinct messages) | Each participant sees the other participant’s current approved profile picture, and both see a notice that pictures are shown. No prompt is shown and no choice is stored. |
| No picture | The owner has no approved profile picture | Show a clear unavailable state. No image is shown. Starting a search requires an approved picture (FR-06), so this arises only when a picture is removed or replaced mid-chat. |
| Paid peek | A peek was bought before the milestone (FR-13) | The buyer alone sees the subject’s permitted ASL and/or picture. The subject’s view is unchanged. |

- **Counting words:** Count words containing letters in committed text messages, capped at 20 per participant. Ignore numbers alone, emoji, punctuation, generated attachment messages, failed writes and stable-ID retries.
- **Counting messages:** A message counts toward the profile reveal only when it contains at least one letter-bearing word and is not an attachment. Identical text after case and whitespace normalization counts once per participant, and a duplicate counts toward neither bar. “Ten messages” means ten distinct qualifying messages, not ten sends. The count is capped at 50 per participant. Numeric-only, emoji-only and punctuation-only messages do not count.
- **Threshold timing:** No elapsed time applies. Words alone never unlock the profile reveal. The Room restores counts for existing open quick chats from their retained encrypted history, with counts and duplicate-message fingerprints saved in Room storage. Counts saved under an older `counts_version` are recounted from history in one pass.
- **Notices and retries:** The picture notice is derived from authoritative room state, so it appears once the milestone is reached and never duplicates. Refresh, reconnect and retries do not change the reveal. Notifications use the existing authenticated room-update path.
- **Scope and authority:** Progress and reveals are scoped to the current quick chat. Next/new matches start with fresh progress and no inherited reveal or peek. Leaving, blocking, expiry or loss of authorization prevents later disclosure and retrieval through this room. Image access keeps the private-media and security boundaries (BE-01, BE-04, BE-06) and rechecks access around R2 reads.

Acceptance criteria, verified at the levels recorded in the implementation matrix (local tests are not production deployment evidence):

| Case | Expected result |
| --- | --- |
| Words A=9, B=10 | ASL is hidden for both. |
| Words A=10, B=10 with messages below 10 | Each sees the other’s permitted ASL in the sidebar. The profile reveal stays hidden. |
| One message of 20 words each, with 1 message each | ASL is shown up to the word cap. The profile reveal stays hidden, because words alone do not unlock it. |
| Messages A=10, B=10 | Each sees the other’s current approved picture, with no prompt and no choice. |
| Messages A=10, B=9 | The profile reveal stays hidden for both. |
| Duplicate, emoji-only, numeric-only or punctuation-only messages | Not counted toward messages; duplicates count toward neither bar. |
| Owner has no approved picture | An honest unavailable state is shown; no image or prompt appears. |
| Picture replaced mid-chat | The owner’s current approved picture is shown. The old picture’s URL no longer resolves, because retrieval checks the picture identity. |
| Peek purchased before the milestone | Only the buyer sees the reveal; the subject’s view is unchanged. |
| Submit after Next, block, leave, expiry or access loss | Reject unauthorized or stale retrieval; do not transfer progress or reveal into the next conversation. |

**Implementation and limits:** [Room](./celld/durable-objects/room.ts) owns the word and message counts, both thresholds and the snapshot reveals. Its snapshots expose `pictureReveal`, `pictureProgress`, `thresholds`, caps and the viewer’s `peek`. [Profile-picture state](./celld/features/profile-pictures/state.ts) is owned by AppCoordinator; authenticated routes use private R2 and bounded format/container checks. Room image reads recheck current access around R2 reads and reject expired or unavailable owners; ASL snapshots also hide unavailable owners. The former consent endpoint `POST /api/rooms/:roomId/picture-sharing` and the `picture.share` command were removed. Basic format validation does not promise full decoding, metadata removal or automated content moderation. Room attachments remain scanner-gated. [Migration 0005](./celld/migrations/0005_profile_pictures.sql) must be applied before production traffic. [Disclosure tests](./tests/fr12.test.ts) cover the milestones, counting, backfill, threshold reconfiguration, consent removal, leave/block/Next, and access rules; [credits tests](./tests/credits.test.ts) cover the peek. Browser coverage is in the disclosure, responsive and credits suites. No production deployment or remote migration is claimed. See [ADR-05](./docs/engineering/ARCHITECTURE_DECISIONS.md#adr-05-credit-wallet-and-ledger-owned-by-appcoordinator) and [ADR-06](./docs/engineering/ARCHITECTURE_DECISIONS.md#adr-06-message-based-profile-reveal-and-removal-of-per-chat-picture-consent). Earlier decisions in [ADR-01](./docs/engineering/ARCHITECTURE_DECISIONS.md#adr-01-private-account-pictures-with-room-scoped-disclosure-consent) are superseded for consent and milestones only.

### FR-13 — Credits economy

**[TARGET] Ships disabled.** Verified accounts hold a soft-currency wallet. Guests never receive a wallet and see a verify prompt instead. Money is not part of this requirement: no live payment gateway exists, and purchase code is a seam ([AD-06](#architecture-decisions)).

| Item | Setting (admin-configurable) | Default |
| --- | --- | --- |
| Feature switch | `credits_enabled` | `false` |
| Verification bonus (once per account) | `credits_verify_bonus` | 50 |
| Daily claim (UTC day) | `credits_daily_base` + `credits_daily_streak_bonus` × (streak − 1), streak capped at `credits_daily_streak_max_days` | 5 + 2 per day, max 7 days |
| Quick-chat profile milestone reward (once per participant and room, at most five rewards per user per UTC day) | `credits_activity_milestone_reward` | 3 |
| Sneak peek of a quick-chat partner | `credits_peek_price` | 10 |
| Contact storage | `credits_contact_slot_base` free, `credits_contact_slot_pack` slots per purchase at `credits_contact_slot_price`, total capped at `credits_contact_slot_max` | 10 free; 5 slots for 15; max 50 |
| Reconnect | `reconnect_price`, charged to the requester on acceptance | 3 |
| Credit packs | Contract data (`CREDIT_PACKS`), not admin settings | Provisional placeholders |

- **While disabled**, the economy is absent: contacts are unlimited, reconnect is free, no grants or purchases happen, and the Credits page is hidden. These are today’s behaviors.
- **Peek:** One-sided, not notified, and scoped to that quick chat. It reveals ASL and/or the subject’s approved picture to the buyer only, is charged once per room, and is refused with 409 when nothing new would be revealed. The client confirms exactly what was shown in the pre-flight; a changed reveal is refused. `aslVisibility` still applies.
- **Reconnect:** Requests are free to send. A requester who cannot pay is refused before sending. An acceptance with insufficient credits expires the request, creates no room and notifies both sides.
- **Contacts:** Saving within free or purchased slots is free. A new contact needs a free slot on both sides at acceptance.
- **Errors:** Insufficient credits return 402. Ungated actions return 403 for guests and disabled features. Repeated requests with the same operation identifier are idempotent.
- **Top-up:** Purchases start a PENDING order and settle only from a verified provider event. A verified PAID event also credits an order that already expired or failed locally, once, because the provider confirms money moved. Until a gateway is configured, the only checkout is the non-production sandbox (AD-06).

Acceptance criteria, verified at the levels recorded in the implementation matrix:

| Case | Expected result |
| --- | --- |
| Verification bonus repeated through verify or OAuth sign-in | Granted exactly once per account. |
| Daily claim repeated within one UTC day; claim on consecutive days; gap of more than one day | At most one grant per day; the streak continues on consecutive days, resets after a gap, and the bonus stops growing at the configured maximum. |
| Guest or disabled feature on each credit route | Denied; no balance or ledger change. |
| Peek repeated, insufficient balance, changed or nothing-new reveal | One debit per room; a repeat is a no-op; an insufficient balance or changed reveal leaves the wallet and peek record untouched. |
| Contact cap on request and on acceptance; purchase replayed with the same operation identifier; purchase beyond the maximum | Enforced; the replay charges nothing; the purchase beyond the maximum is refused. |
| Reconnect pre-flight, acceptance charge, and acceptance with insufficient funds | The charge lands once on the requester; the insufficient case creates no room and leaves no partial state. |
| Webhook replayed or with a bad signature; sandbox in production | Replays settle once; a bad signature is rejected; the sandbox never exists in production. |
| Mixed grants and spends | The ledger reconciles with the wallet balance. |

**Implementation and limits:** [Wallet domain](./celld/features/credits/wallet.ts) builds the D1 statements; [AppCoordinator](./celld/durable-objects/app.ts) owns every balance change; [migration 0006](./celld/migrations/0006_credits.sql) defines the tables and append-only ledger triggers. Activity rewards are queued outbox effects delivered by the Room job path. The Credits page and quick-chat peek UI are in [App](./src/App.tsx) and [CreditsPage](./src/CreditsPage.tsx). See [ADR-05](./docs/engineering/ARCHITECTURE_DECISIONS.md#adr-05-credit-wallet-and-ledger-owned-by-appcoordinator) and [ADR-06](./docs/engineering/ARCHITECTURE_DECISIONS.md#adr-06-message-based-profile-reveal-and-removal-of-per-chat-picture-consent). No live gateway, production deployment or remote migration is claimed.

## End-to-end application flows

**[CURRENT]** These are the implemented flow paths. Provider-dependent steps remain **[CONDITIONAL]** as noted above.

1. **Enter and identify:** Open the app or an invitation, choose guest or configured sign-in, confirm nickname/profile, and retain the invitation until entry is authorized or a pending/rejected state is shown.
2. **Create and join:** Validate room input, let AppCoordinator record a recoverable creation operation, initialize the authoritative Room, publish required D1 projections, and return the invitation. Joining must follow current eligibility and host approval rules.
3. **Chat:** Load authorized room/history, subscribe to the room socket, submit a REST message with a stable client ID, and commit ciphertext plus durable effects. Notifications trigger authoritative reads; duplicate submissions must not duplicate messages.
4. **Meet and connect:** Check eligibility and blocks, hold a matching lease or respond to a relationship request, and initialize/recover the appropriate conversation. Cancel, Next, leave and block must preserve existing restrictions and consent.
5. **Moderate and expire:** Authorize the action, commit the state change, revoke applicable access, and deliver retryable notifications/projections/cleanup. Authorization deadlines apply even if asynchronous cleanup has not run yet.

## Backend requirements and ownership

**[CURRENT]** The ownership and backend mechanisms below exist in source. Instructions to preserve them are ongoing implementation requirements, not a guarantee that every failure case has been audited.

| Owner                                    | Authoritative responsibility                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Hono Worker                              | Public validation, authentication context, origin/CSRF checks, authorization routing, sanitized errors and provider boundaries |
| D1                                       | Users, sessions, identity flows, profiles, relationships, settings, reports, audits and durable global operations              |
| AppCoordinator                           | Serialized identity/global commands, room initialization, matching reservations and recoverable relationship operations        |
| Room Durable Object                      | Membership, encrypted messages, invitations, moderation, room lifecycle, sockets and local outbox                              |
| Matcher / UserHub                        | Matching leases and selection / presence leases, notification sockets and user limits                                          |
| Discovery / RateLimiter                  | Discovery invalidations / anonymous request limits                                                                             |
| R2 / Queues / alarms / scheduled handler | Private media / durable effect delivery and cleanup                                                                            |

- **BE-01 — Authorization authority [CURRENT]:** D1 room, membership, invitation and entity indexes are query aids. They do not grant permission. Consult the owning authority for history, membership changes, uploads/downloads and socket activity. Recheck current permissions for delivery and revocation; client state is never authorization evidence. **[ISSUE]** [IMP-01](./docs/IMPLEMENTATION_REVIEW.md#imp-01), [IMP-03](./docs/IMPLEMENTATION_REVIEW.md#imp-03).
- **BE-02 — Consistency [CURRENT]:** Keep room-local mutations and their outbox records in synchronous SQLite transactions. Serialize global operations through AppCoordinator and atomic D1 batches. Keep external provider work outside local transactions. Publish versioned projections; stale retries must not overwrite newer state. Acknowledgments wait for the required authoritative commit/projection. **[ISSUE]** [IMP-04](./docs/IMPLEMENTATION_REVIEW.md#imp-04).
- **BE-03 — Recovery [CURRENT]:** Persist effects before dispatch. Retain outbox work until completion, make delivery idempotent, and tolerate duplicates and interruptions. Queue delivery is at least once. Alarms and scheduled recovery must preserve eventual retry after queue exhaustion. Use durable alarms/leases for backend deadlines, not process-local timers as the sole mechanism. **[ISSUE]** [IMP-02](./docs/IMPLEMENTATION_REVIEW.md#imp-02).
- **BE-04 — Confidentiality [CURRENT]:** Store message ciphertext using the existing AES-256-GCM format and room authenticated data. **[POLICY]** Preserve `MESSAGE_KEY` for retained data or design an explicit migration. **[CURRENT]** This is backend encryption at rest, **not end-to-end encryption**: the authorized backend decrypts content. **[POLICY]** Keep secrets out of source, frontend assets, logs, checkpoints and committed configuration.
  - **Cloudflare credential placement audit:** Treat `wrangler.cloudflare.jsonc` and `wrangler.staging.jsonc` as source-controlled configuration. Use `vars` only for nonsecret settings. Store `MESSAGE_KEY`, OAuth client secrets, provider API keys and other credentials as Worker secrets for the matching production or staging Worker. Do not add a secret-name entry to `vars`, even with an empty or placeholder value. `GOOGLE_CLIENT_ID` is an app identifier and may be a nonsecret variable; `GOOGLE_CLIENT_SECRET` is a secret. Use D1 and R2 bindings rather than adding storage credentials when the app uses those Cloudflare resources.
  - **Pre-deployment and exposure audit:** Review the deployment config and pending Git diff for credential values or secret-named `vars` before publishing; mask values in audit output. Confirm each secret belongs to the intended Worker environment. If a real credential was committed, pushed, or otherwise shared, remove it from configuration and rotate/revoke it at the provider; deleting it from the latest file does not remove it from Git history.
- **BE-05 — Boundary security [CURRENT]:** Preserve HttpOnly sessions, Secure production cookies, CSRF validation, exact configured browser origins, input/size limits and remaining rate limits. Message submissions have no global per-user 40-messages-per-minute cap; room slow mode and rate limits on other endpoints remain. Production browser origin must match the deployed app. **[POLICY]** Accept a client-IP header only when the hosting ingress supplies it. **[CURRENT]** Cloudflare production is configured to use `CF-Connecting-IP`.
- **BE-06 — Media safety [CONDITIONAL]:** Room attachments require scanner configuration and remain quarantined until validated sanitized output exists. Profile pictures use the authenticated private upload path with bounded format/size checks and no external scanner; this does not claim full decoding, metadata removal or automated content moderation. Keep R2 private. Approval and download recheck access; failed deletions and call termination remain retryable durable effects. **[ISSUE]** [IMP-02](./docs/IMPLEMENTATION_REVIEW.md#imp-02).
- **BE-07 — Persistence evolution [POLICY]:** Append migrations rather than rewriting applied history. Preserve existing Durable Object names, bindings and migration history unless the task authorizes a compatible migration. **[CURRENT]** Production checks that required D1 migrations have been applied, and separate configurations identify Cloudflare and Celld targets. **[POLICY]** Apply migrations before traffic and retain that target separation. **[ISSUE]** [IMP-11](./docs/IMPLEMENTATION_REVIEW.md#imp-11).
- **BE-08 — Credit ledger and wallet [TARGET]:** `credit_entries` is append-only; update and delete are rejected by triggers (migration `0006_credits.sql`). AppCoordinator owns every balance change in one atomic D1 batch inside its serialized command (BE-02). Each change is idempotent on `entry_key`: grant and spend statements are gated with `NOT EXISTS` on that key, and ledger inserts are `ON CONFLICT DO NOTHING`. Overdrafts are refused by `CHECK(balance >= 0)`, which aborts the whole batch, and by a balance pre-check. `balance_after` reconciles with `credit_wallets.balance`. Payment webhooks are authenticated only by an HMAC signature over the raw body, using `CREDITS_WEBHOOK_SECRET` as a Worker secret (BE-04). Settlement is at least once and idempotent on `(provider, provider_reference)`. Room reward effects go through the queue (BE-03) and are keyed per participant and room. Migration `0006_credits.sql` must be applied before production traffic, like `0005`.

## Architecture decisions

- **AD-01 — Public API [CURRENT]:** Hono REST/JSON is the implemented public command/query contract. Shared schemas validate requests. Internal Worker-to-Durable-Object calls use the runtime RPC surface; WebSocket upgrades use the object's fetch surface. **[NOT IMPLEMENTED]** GraphQL is not part of the current API.
- **AD-02 — Realtime [CURRENT]:** Authenticated WebSockets carry user notifications, active-room events and discovery invalidations. Message writes remain REST; socket input is typing/ping. Clients recover authoritative state after reconnect and handle revocation. The active room uses its room socket to determine connection status and start fallback. Presence HTTP failures leave that socket state intact. **[NOT IMPLEMENTED]** SSE is not part of the current realtime transport. **[POLICY]** Prefer existing push channels for new live updates rather than adding unconditional refetch loops.
- **AD-03 — Justified timers [CURRENT]:** The client sends a presence heartbeat every 25 seconds and skips a timer tick while a heartbeat is pending. A disconnected active room checks for updates every five seconds, skipping ticks while a refresh is pending. Socket recovery stops the fallback timer and triggers a catch-up refresh. Transient refresh failures retain the current view and retry after five seconds with exponential backoff capped at 30 seconds, extended when the server asks for a longer `Retry-After`. Leaving the room cancels pending refreshes and retry timers. Match requests run every five seconds while queued for at most two minutes, and pending-join checks run every four seconds. The Matcher expires queue entries at the same two-minute deadline. [src/realtime.ts](./src/realtime.ts) pings every 25 seconds and reconnects with capped exponential backoff and jitter. **[POLICY]** Preserve cleanup and document the purpose, interval, lifecycle and outage behavior of changed timers.
- **AD-04 — Runtime and configuration [CURRENT]:** `wrangler.cloudflare.jsonc` defines Cloudflare production and PR Preview resources; `wrangler.staging.jsonc` defines isolated Cloudflare staging resources and its `workers.dev` origin. PR Previews use explicitly selected configuration, per-Preview Durable Object namespaces, shared staging D1/R2/queue resources, synthetic data and a dedicated Preview key. Worker secrets supply sensitive values. `wrangler.jsonc` and `.env` support the Celld path. Cloudflare builds read the selected target's public settings for security headers; secrets are uploaded separately. Local ports come from workspace allocation or explicit overrides. **[POLICY] Branch isolation:** GitHub checks run on pushes to `staging` and `main` and pull requests targeting either branch. Cloudflare production uses `main` and staging uses `staging`, each with its own Wrangler configuration and isolated resources. Cloudflare publishing scripts enforce that branch/target match using `WORKERS_CI_BRANCH` in Workers Builds and the checked-out Git branch locally. A staging push must not update the active production deployment; disable production preview builds as well when staging pushes must not trigger any production Worker build. Merge to `main` is the production promotion point when Cloudflare automatic deployment is enabled. Cloudflare Workers Build branch controls remain external configuration and require runtime confirmation. **[ISSUE]** [IMP-09](./docs/IMPLEMENTATION_REVIEW.md#imp-09), [IMP-10](./docs/IMPLEMENTATION_REVIEW.md#imp-10), [IMP-11](./docs/IMPLEMENTATION_REVIEW.md#imp-11).
- **AD-05 — Proportionate changes [POLICY]:** Reuse existing contracts and authorities. Transport replacement, a second source of truth, an encryption format change or a new persistence service is a material architecture change. When the task authorizes one, record: requirement/problem; chosen design and rejected alternatives; affected contracts/state; migration and rollback; security/recovery implications; acceptance evidence. Update this decision section or link an ADR. Routine implementation choices do not require a separate approval ceremony.
- **AD-06 — Gateway-agnostic payment seam [TARGET]:** `CreditPaymentProvider` (`createCheckout`, `verifyWebhook`) is the only payment integration point. The sandbox adapter is the only implementation. It is unavailable when `NODE_ENV=production` and requires `CREDITS_SANDBOX=true` plus `CREDITS_WEBHOOK_SECRET`; it is a free-money path if it ever leaks. No live gateway is configured or claimed. A real gateway needs a new decision record. See [ADR-05](./docs/engineering/ARCHITECTURE_DECISIONS.md#adr-05-credit-wallet-and-ledger-owned-by-appcoordinator).
